# 2회차 실습 — 파싱 · 검증 게이트 · 청킹

수업은 "강사가 짧게 보여 주고 → 여러분이 직접 코드를 채우고 → 테스트로 확인" 을 세 번 반복합니다. 그 세 번을 **실습 1 · 2 · 3** 이라고 부릅니다. 아래는 수업 순서대로 적은 것입니다.

**이 문서에서 쓰는 명령**

| 명령 | 하는 일 |
|---|---|
| `make test` | 자동 채점. `tests/test_parsing.py` 의 검사 21개를 한 번에 돌려서 맞으면 초록, 틀리면 빨강 |
| `make chunk-sample` | 문서 6건을 파싱 → 검사 → 청킹 순서로 돌려서 문서마다 한 줄씩 결과를 찍는다. 7초 |
| `make chunk` | 같은 일을 문서 51건 전부에. 4~5분. 결과는 `data/chunks/chunks.jsonl` |
| `make check-s02` | 청크 파일이 조건 6개를 만족하는지 검사한다. 과제 확인도 이 명령으로 |

## 오늘 끝내고 갈 것

1. 같은 PDF 를 파서 세 개에 넣으면 **결과가 어떻게 달라지는지** 직접 봅니다
2. 나쁜 결과를 **숫자로 재서 걸러내는 검사기(게이트)** 를 만듭니다 — LLM 없이
3. 문서를 **조항 단위로 잘라**, 조각마다 고정된 청크 ID를 붙입니다

> 오늘 만든 청크 ID 가 8회차까지 그대로 갑니다. 여기서 형식을 바꾸면 골든셋의 정답 근거가 전부 어긋납니다.

## 데모 1 · 같은 PDF, 세 파서

강사 화면의 노트북 `notebooks/s02_parsers.ipynb` 셀 1~8 을 봅니다. 셀 번호는 코드 셀 첫 줄의 `# [셀 N]` 표시입니다. 자기 노트북에서 같이 실행해도 되고(`make notebook`), 보기만 해도 됩니다. 볼 것은 세 가지입니다.

**하나은행 2009 여신거래기본약관.** pdfplumber 가 76,979자를 추출하고 PyMuPDF 는 7,847자를 추출합니다. 글자 수만 보면 pdfplumber 가 열 배 가까이 많은데, 한글 열을 보면 pdfplumber 는 0자입니다. `(cid:1104)(cid:2687)…` 같은 글자 번호가 글자로 나온 것입니다. 2009년 PDF 라 폰트에 "이 번호는 이 글자다"라는 표가 없습니다. 글자 하나가 열 글자짜리 번호로 나오니 글자 수만 열 배로 부푼 것입니다. **"글자가 나왔다"와 "읽을 수 있다"는 다릅니다.** 이 한 줄이 오늘 검사기의 존재 이유입니다.

**금감원 예금거래기본약관.** 이번에는 반대입니다. 한글은 셋 다 5,625자로 같은데 PyMuPDF 의 공백 비율이 0.026 입니다. 띄어쓰기를 잃었습니다. 띄어쓰기가 없으면 키워드 검색이 단어를 못 나누고(4회차 BM25 가 망가집니다), 사람이 근거를 못 읽고, 조항 제목 정규식이 안 맞습니다(오늘 실습 3 이 어긋납니다).

**그래서 파서에 따라 결과가 달라지는 문서는 몇 건인가.** 51문서 중 6건입니다. 파서에 따라 한글이 나오거나 안 나오는 문서 1건, 파서에 따라 띄어쓰기가 살거나 사라지는 문서 5건. 나머지 45건은 어느 파서를 써도 같습니다. 6건 때문에 파이프라인 전체를 복잡하게 만들지 않고, 그렇다고 6건을 버리지도 않는 방법이 검사기입니다 — 기본 경로는 단순하게 두고, 품질을 재 봐서 기준에 못 미친 것만 다른 길로 보냅니다.

노트북에서 재는 다섯 지표(글자 수 · 한글 수 · 공백 비율 · 깨진 문자 비율 · 단음절 토큰 비율)가 그대로 실습 2 의 지표입니다.

## 데모 2 · 표와 OCR

셀 9~12. 약관에서 숫자는 표 안에 있습니다 — 중도해지이율, 수수료율, 자기부담금, 한도. 표를 그냥 글자로 펴 버리면 의미가 무너집니다.

pdfplumber 는 합쳐진 칸을 "첫 칸은 값, 나머지는 `None`" 으로 냅니다. `None` 을 버리고 이어 붙이면 「현행 | 개정(안) | 비고」가 뒤섞입니다. 문서마다 `None` 비율이 다르고(카카오뱅크 정기예금 69.9%, iM 주택담보대출 6.0%), 높을수록 합쳐진 칸이 많은 복잡한 표입니다. 표를 글자로 바꾸는 방법은 마크다운 표(구조 보존, 표 전체가 한 덩어리)와 행 단위 문장(행이 잘 걸림, 헤더가 반복됨) 둘을 봅니다. 정답은 없고 4회차에 두 방식으로 인덱싱해 Recall 을 잽니다.

OCR 은 수업 중에 돌리지 않습니다. 스캔본 8쪽에 몇 분이 걸리고, 엔진이 OS 마다 다르고, 여섯 명이 각자 돌리면 여섯 가지 결과가 나옵니다. 대신 **강사가 미리 돌려 둔 결과(캐시)를 읽는 구조**만 봅니다. 디스코드의 `ocr_cache.zip` 을 `data/` 안에 풀어 `data/ocr_cache/` 가 있으면 셀 12 에서 8쪽이 나오고, 없으면 "캐시가 없습니다"가 나옵니다. 캐시에 원본 PDF 의 SHA-256 이 들어 있어 원본이 바뀌면 경고를 냅니다. 낡은 OCR 결과로 인덱스를 만드는 것이 가장 찾기 어려운 에러입니다 — 검색은 잘 되는데 답이 미묘하게 틀리고, 원본을 열어 보면 맞게 적혀 있습니다.

## 데모 3 · 기준값은 어디서 오나

셀 13~15. 코퍼스 1,306쪽 전체를 재서 네 가지 수치의 분포를 봅니다. **기준값을 감으로 정하지 않습니다.**

- 띄어쓰기가 사라진 쪽 138쪽(10.6%) — 대부분 실손 표준약관. PyMuPDF 로 만들어서 그렇고, pdfplumber 로 다시 추출하면 살아납니다. 검사기가 "다시 추출해라(reparse)"로 보내는 것이 정확히 이 경우입니다.
- 폰트 깨짐 4쪽(0.3%) — 드물지만 걸리면 심각합니다.
- 단음절 토큰 0쪽 — 그래도 빼지 않습니다. 글자가 한 자씩 떨어진 문서가 나타나면 0.9 를 넘고, 안 걸리는 검사의 비용은 0 입니다. 다만 "0쪽"이라는 사실은 기록합니다.
- 공백 기준값을 0.01 / 0.02 / 0.04 로 움직이면 7쪽 / 138쪽 / 426쪽. 너무 느슨하면 놓치고, 너무 빡빡하면 멀쩡한 표 페이지까지 다시 추출하는 줄에 섭니다. 0.02 를 고른 이유가 여기 있습니다. 자기 값을 골라도 되고, 고른 이유를 선택 과제에 적으면 됩니다.

## 실습 2 · `judge_page`

`src/finrag/parsing/validate.py` 의 `judge_page` 를 채웁니다.

**먼저 읽을 것.** 파일 위쪽의 기준값 상수 다섯 개와 그 옆 주석, `score_page` 가 반환하는 dict 의 키 다섯 개(`chars`, `hangul_ratio`, `broken_ratio`, `space_ratio`, `single_char_token_ratio`), 함수 안의 힌트 주석.

**규칙.** 쪽 하나를 보고 `pass` / `reparse` / `ocr` 중 하나와 이유 목록을 반환합니다.

- 글자가 `MIN_CHARS_PER_PAGE` 보다 적으면 글자 층이 없는 것입니다. 이미지 객체가 있으면(`has_image`) 스캔본이니 `ocr`, 없으면 그냥 빈 페이지니 `pass`.
- 글자는 있는데 한글 비율이 낮거나, 깨진 문자 비율이 높거나, 공백 비율이 낮거나, 단음절 토큰 비율이 높으면 걸린 수치마다 이유를 적고 `reparse`. 하나도 안 걸리면 `pass`.
- `skip_space` 가 참이면 공백 검사를 건너뜁니다. 표 때문에 우리가 일부러 PyMuPDF 로 바꿔 끼운 페이지는 공백이 적은 게 당연한데, 그걸 벌주면 안 됩니다.

이유 문자열은 "한글 비율 0.000 < 0.1" 처럼 값과 기준값을 같이 적습니다. 나중에 로그만 보고 왜 걸렸는지 알 수 있어야 합니다.

```bash
make test
```

`judge_page` 테스트 6개가 초록이면 됩니다. 문서를 받았으면 `test_gate_routes_scan_to_ocr` (스캔본은 OCR 로 가야 한다) 도 같이 초록이 됩니다.

**왜 LLM 을 안 쓰나.** 문서 51건에 LLM 을 돌리면 비용 · 시간 · 재현성이 다 나빠집니다. 검사기는 같은 문서를 넣으면 항상 같은 판정을 내야 합니다. 그래야 "어제와 다른 결과"를 디버깅할 수 있습니다. 3회차에 LLM 복구 경로를 붙이는데, 그건 검사기가 걸러낸 소수에만 씁니다.

**일부가 깨졌다고 전체를 버리지 않습니다.** 실손 표준약관은 492쪽 중 55쪽 하나에 깨진 문자 89개가 있습니다. 문서 판정을 "나쁜 페이지가 하나라도 있으면 실패"로 두면 골든셋 근거 문서 5건이 사라집니다. 그래서 같은 파일의 `validate` 는 쓸 수 있는 페이지 수로 문서를 판정하고, 나쁜 페이지는 지우지 않고 표시만 합니다. 그 부분은 이미 구현돼 있으니 읽어만 둡니다. 지난 시간 질문의 답이 이 함수입니다.

## 실습 3 · `split_articles`

블록 하나는 이런 dict 입니다.

| 키 | 무엇 |
|---|---|
| `article` | 통일한 조항 표기. `"제31조"`. 첫 조항 머리글 앞의 본문은 `""` |
