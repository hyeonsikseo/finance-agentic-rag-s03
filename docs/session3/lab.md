## 1부 · 원칙 두 가지

**인제스천 그래프에 LLM 노드는 0개입니다.** 문서 51건을 LLM 에게 읽히면 돌릴 때마다 비용이 들고, 몇 분이 걸리고, 같은 문서에서 다른 결과가 나오고, "왜 이렇게 됐나"를 설명할 수 없습니다. 지난 시간 검사기가 숫자로 판정하는 이유가 그것이었고, 오늘 그래프도 같습니다. LLM 은 검사기가 걸러낸 소수의 실패 문서에만 쓰고, 그마저도 오늘은 선택 과제입니다.

**LangGraph 는 스케줄러가 아닙니다.** LangGraph 가 해 주는 것은 분기(조건부 엣지), 상태, 지나온 경로의 기록입니다. "매일 새벽 3시에 돌려라", "실패하면 다시 시도해라", "밀린 문서를 처리해라"는 해 주지 않습니다. 그게 필요하면 Airflow · Prefect 이고, 둘은 층이 다릅니다. Airflow 가 "언제 돌릴지"를, LangGraph 가 "이 문서 하나를 어느 길로 보낼지"를 맡습니다.

## 데모 1 · 상태 하나를 노드가 차례로 고친다

노트북 `notebooks/s03_langgraph.ipynb` 셀 1~4. 셀 번호는 코드 셀 첫 줄의 `# [셀 N]` 표시입니다. 자기 노트북에서 같이 실행합니다(`make notebook`). 실습 1 이 이 노트북 안에 있습니다.

- **State** — 노드들이 주고받는 딕셔너리 하나. 어떤 키가 있는지 `TypedDict` 로 적어 둡니다. 적지 않은 키는 노드가 반환해도 버려집니다.
- **Node** — 그냥 함수입니다. 상태를 받아서 **바뀐 키만** 담은 딕셔너리를 반환합니다.
- **Edge** — 다음 노드. 항상 같은 방향이면 보통 엣지, 상태에 따라 갈리면 조건부 엣지.

오늘 코드(`src/finrag/ingestion/`)에서는 `IngestState` 가 State 이고, `classify` · `parse` · `gate` … 가 노드입니다.

## 실습 1 · 라우터 함수 한 줄

노트북 셀 5 의 `route_after_grade` 를 채웁니다. 몸풀기입니다. 한 줄이면 됩니다.

조건부 엣지에 쓰는 함수를 **라우터**라고 부릅니다. 라우터는 노드가 아닙니다. 상태를 읽기만 하고, 다음 목적지의 **이름(문자열)** 을 반환합니다. `grade` 가 `"sufficient"` 면 `"answer"`, 아니면 `"abstain"` 입니다.

셀을 실행해서 **"실습 1 통과"** 가 나오면 됩니다. 그다음 셀 6~8 을 이어서 실행합니다. 셀 7 에서 질문 두 개의 경로가 `retrieve → grade → answer` 와 `retrieve → grade → abstain` 으로 갈리는 것을 봅니다. 오늘 인제스천 리포트의 "경로별 문서 수"가 바로 이 경로를 문서 51건에 대해 센 것입니다.

오늘 코드의 `nodes.route_after_gate` 가 정확히 이 모양입니다. 거기서는 `state["route"]` 를 그대로 반환합니다.

## 인제스천 그래프

```
classify → parse → gate ─┬ pass    → chunk → END
                         ├ reparse → reparse ─┬ pass → chunk
                         │                    ├ ocr  → ocr
                         │                    └ 쓸 쪽이 없음 → llm_repair
                         ├ ocr     → ocr ─────┬ chunk
                         │                    └ fail → dead_letter
                         └ fail    → dead_letter
```

| 노드 | 하는 일 | 지난 시간의 무엇 |
|---|---|---|
| `classify` | 파일의 첫 바이트로 형식을 정한다 (pdf / text / office / missing) | — |
| `parse` | 기본 파서로 추출한다 | `extract` |
| `gate` | **실습 2.** 검사기에 넣고 판정을 `route` 에 적는다 | `validate` |
| `reparse` | 나쁜 쪽만 다른 파서로 갈아 끼운다 | 2회차 노트북의 파서 바꿔 추출하기 |
| `ocr` | OCR 캐시를 읽어 이미지 쪽을 채운다 | `load_ocr` |
| `llm_repair` | 쓸 쪽이 하나도 없을 때만 LLM 에게 복원시킨다 (선택 과제) | — |
| `chunk` | 조항 단위로 자른다 | `chunk_document` |
| `dead_letter` | 사람 검토 큐. 이유를 남기고 끝낸다 | — |

노드 8개는 이미 있습니다. 여러분이 채우는 것은 둘, `gate`(판정)와 `build_ingest_graph`(연결)입니다.

## 실습 2 · `gate`

`src/finrag/ingestion/nodes.py` 의 `gate` 를 채웁니다. 지난 시간의 검사기 `validate` 를 그래프 노드로 만드는 일입니다.

**먼저 읽을 것.** 파일 위쪽의 `IngestState`, 바로 위의 `classify` 와 `parse` 가 상태에 무엇을 넣는지(`route`, `pages`, `parser`), 함수 안의 힌트 주석.

**규칙.**

- `state["route"]` 가 `"office"` 나 `"missing"` 이면 검사기에 넣지 않고 바로 `fail` 입니다. 리포트(`report`)에는 `doc_id`, `verdict: "fail"`, `reasons: ["지원하지 않는 형식(office)"]`, 그리고 빈 `pages` · `bad_pages` 를 넣습니다.
- 아니면 `parse` 가 추출한 `pages` 를 `Extraction(doc_id, parser, pages)` 으로 싸서 `validate` 에 넣습니다. PDF 면 `page_objects(path)` 도 같이 넣습니다(이미지 쪽을 알아야 OCR 판정이 됩니다). 텍스트 문서면 빈 목록입니다.
- 반환하는 것은 둘입니다. `report` 는 `rep.to_dict()`, `route` 는 `rep.verdict`.

**왜 office 를 검사기에 안 넣나.** 넣어 봐야 "글자 0자"라는 같은 답만 나오고, 사람 검토 큐에서 "왜 여기 왔나"가 흐려집니다. 형식 때문에 못 읽은 것과 글자가 깨진 것은 다른 문제입니다.

**검사기의 마지막 규칙이 바뀌었습니다.** 지난 회차에는 쓸 수 있는 쪽이 하나도 없고 이미지도 없으면 바로 `fail` 이었습니다. 지금은 깨진 쪽이라도 있으면 `reparse` 로 보내서 다른 파서로 고쳐 보고, 그래도 안 되면 `llm_repair` 까지 갑니다. 글자도 이미지도 없는 문서만 게이트에서 바로 `fail` 입니다(`src/finrag/parsing/validate.py` 의 마지막 분기).

## 실습 3 · `build_ingest_graph`

`src/finrag/ingestion/graph.py` 의 `build_ingest_graph` 를 채웁니다. 노드 등록과 `compile()` 은 뼈대에 있고, 엣지 연결만 채웁니다. 12~15줄입니다.

```python
g.set_entry_point("classify")
g.add_edge("classify", "parse")
g.add_conditional_edges("gate", N.route_after_gate,
                        {"pass": "chunk", "reparse": "reparse", "ocr": "ocr", "fail": "dead_letter"})
```

이런 줄을 위 그림대로 채웁니다. 조건부 엣지는 `add_conditional_edges(노드, 라우터, {라우터가 돌려주는 값: 다음 노드})` 입니다. 라우터는 `nodes.py` 에 `route_after_gate` · `route_after_reparse` · `route_after_ocr` 로 있고, `llm_repair` 다음은 `lambda s: s["route"]` 를 씁니다. 끝은 `chunk → END`, `dead_letter → END`. END 로 가는 엣지가 없어도 컴파일과 실행은 되지만, 그래프에 끝이 없는 노드가 남고 테스트가 그것을 잡습니다.

| 판정 | 문서 | 어떤 문서 |
|---|---|---|
| pass | 40 | 어느 파서로도 잘 읽히는 문서 |
| reparse | 5 | ABL 암보험(6쪽 한 장), 하나은행 2009(2쪽), 실손 표준약관 정본(492쪽 중 45쪽), 실손 표준약관 게시본(16쪽), 띄어쓰기가 사라진 한 쪽짜리 손보협회 공시(못 고쳐서 LLM 복구 → 키가 없어 사람 검토 큐) |

끝나면 `data/ingest_report.json` 을 엽니다. 볼 것 세 가지: 경로별 문서 수의 합이 문서 수와 같은가(샌 문서가 없는가), 실패 목록 3건이 1회차 품질 분류표에서 "파싱불가"로 찍은 문서와 같은가, `reparse` 인데 청크가 나왔는가(나쁜 쪽만 갈아 끼우고 문서는 살렸다는 뜻).

게이트 판정(`verdicts`)의 fail 은 2건인데 실패 목록(`failed`)은 3건입니다. 손보협회 공시는 `reparse` 판정 뒤 LLM 복구까지 갔다가 키가 없어 사람 검토 큐로 왔기 때문이고, 그 문서의 `warnings` 에 "LLM 키가 없어 복구를 건너뜀" 이 적혀 있습니다. 판정과 경로는 다른 것입니다.

**같은 파일을 다시 넣으면 건너뜁니다.** `pipelines/ingest.py` 는 문서마다 파일 내용의 해시를 ID(`thread_id`)로 씁니다. 이미 끝난 문서는 다시 파싱하지 않고, 파일이 한 글자라도 바뀌면 다른 ID 가 되어 다시 처리됩니다. 어떻게 되는지는 그 파일의 주석에 적어 두었습니다.

## Qdrant · 청크를 벡터 DB 에 넣는다

```bash
make index
```

청크 하나를 숫자 1,024개짜리 벡터로 바꿔서(임베딩) Qdrant 에 넣습니다. 컬렉션은 이렇게 생겼습니다.

| 무엇 | 오늘 값 | 왜 |
|---|---|---|
| 벡터 | BGE-M3, 1024차원, 코사인 | 한국어와 긴 문서에 강한 공개 모델 |
| 벡터 이름 | `dense` | 4회차에 키워드 벡터(`sparse`)를 같은 컬렉션에 넣습니다. 이름을 안 붙이면 그때 컬렉션을 다시 만들어야 합니다 |
| payload 인덱스 | `doc_type` · `issuer` · `effective_from` … 17개 | 인덱스가 없으면 필터가 전수 스캔이 됩니다. 파일 방식에서는 만들어지지 않고 서버에서만 만들어집니다 |
| 어디서 도나 | 파일(`data/qdrant_local`) | 도커 없이 돕니다. 실무에서는 서버로 띄우고 `.env` 한 줄만 바꿉니다 |

임베딩은 **강사 스냅샷을 재사용**합니다. 청크 3,700개를 CPU 로 임베딩하면 약 25분(M2 기준)인데, 스냅샷을 재사용하면 10초입니다. 스냅샷은 "청크 본문의 해시 → 벡터" 라서 본문이 같은 청크만 재사용하고 다른 것은 계산합니다. 문서 한두 건이 빠진 분도 몇 초면 됩니다. 같은 스냅샷을 쓰는 이유가 하나 더 있습니다. 각자 임베딩하면 부동소수점 차이로 벡터가 미세하게 달라지고 "내 숫자가 왜 강사와 다르지"가 시작됩니다.

출력 맨 위에 `Payload indexes have no effect in the local Qdrant` 경고가 한 줄 나옵니다. 파일 방식에서는 인덱스를 만들지 않는다는 뜻이고 에러가 아닙니다.

필터 쿼리를 하나 해 봅니다.

```bash
.venv/bin/python scripts/search_demo.py "중도해지이율" --issuer 카카오뱅크
```

같은 은행의 판본 세 개(2024 특약, 2026 상품설명서 둘)가 한꺼번에 나옵니다. 1회차에서 본 "판본이 세 개" 문제가 여기서 풀리기 시작합니다. 지금은 필터를 손으로 넣고, 5회차에 LLM 이 질문에서 필터를 추출합니다. `--doc-type 상품설명서` 처럼 문서 종류로도 걸러 볼 수 있습니다.

골든셋 40문항을 벡터 검색(Dense)만으로 풀고, 정답 청크가 상위 몇 번째에 나왔는지 측정합니다.

| 지표 | 강사 값 | 뜻 |
|---|---|---|
| Recall@1 | 40.0% | 첫 번째가 정답인 문항이 40개 중 16개 |
| Recall@5 | 75.0% | 상위 5개 안에 정답이 있는 문항이 40개 중 30개 |
| Recall@10 | 80.0% | 10개까지 넓혀도 8개는 못 찾는다 |
| MRR | 0.532 | 정답이 평균 두 번째쯤에 나온다 |

여러분 화면은 문서 49건이라 MRR 이 0.542 로 살짝 다르게 나옵니다(열화 재현본 2건이 없어서). Recall@5 는 같습니다.

**Recall@5 와 MRR 을 적어 두세요.** 뒤에 키워드 검색(Hybrid), 에이전트, 3단계 비교표를 만들 때 계속 옆에 놓고 봅니다. "75%가 좋은 건가요?"는 지금 알 수 없습니다. 비교 대상이 없기 때문에 오늘 이 숫자를 만드는 겁니다.

전체 평균만 보면 안 됩니다. 유형별로 보면 조항번호형 · 표수치형 · 복합형은 100% 인데 계산형은 40% 입니다. 미답변형 0% 는 맞는 0% 입니다. 근거가 코퍼스에 없는 질문이라 못 찾는 게 정상이고, 5회차에 "거절"로 바꿉니다.
